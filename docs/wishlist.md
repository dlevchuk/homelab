# Changedetection.io and wishlist prices

[← Repository overview](../README.md)

Pi 4 runs `ghcr.io/dgtlmoon/changedetection.io:latest` through the existing
`docker_apps` role. Set `changedetection_image` to a tested tag/digest to pin it;
the initial image pull and ARM64 runtime must be verified on the Pi.
The container binds **the Pi’s Tailscale IPv4 address:5000** and **127.0.0.1:5000**,
with two fetch workers and a one-hour
minimum check interval. Configure each watch for six hours. Datastore:
`/home/pi/docker/changedetection` (private, included in Docker backups and restore).
These backups contain API and Telegram credentials. No browser container is
installed; JavaScript shops need a separately verified ARM64 browser backend.

## Bootstrap and Telegram

Deploy from this repository root:

```bash
ansible-playbook -i ansible/raspberry/hosts ansible/raspberry/site.yml \
  --limit rpi-pi4 --tags changedetection \
  -e ansible_ssh_private_key_file="$HOME/.ssh/raspberry"
```

Open `http://raspberrypi.tail72e9f.ts.net:5000` from a device connected to your tailnet.
Set a UI password and copy the key from Settings → API. The Glance/Homepage
link points to this address; run the full playbook or the `glance` tag to refresh
it. No SSH tunnel is needed. Tailnet ACLs must allow port 5000.

`changedetection_tailscale_enabled: true` on Pi 4 makes Ansible discover and
validate its local Tailscale IPv4 using `tailscale ip -4`; a missing address
fails deployment instead of publishing on all interfaces. Loopback remains
available for the exporter and notification provisioning. The port is not bound
to LAN addresses or `0.0.0.0`. The default on other hosts remains loopback only.
If the Pi receives a different Tailscale IPv4, rerun the playbook to update the
Docker binding. Tailscale must be running before the container starts.

Supply `CHANGEDETECTION_API_KEY`, `TELEGRAM_TOKEN` and `TELEGRAM_TO` to the
Ansible controller environment, or override the corresponding
`changedetection_api_key`, `changedetection_telegram_token` and
`changedetection_telegram_chat_id` through Ansible Vault. Then rerun the command.
The API key is generated by the application, not set by an invented env option.
Without it the container starts, but notification provisioning is skipped.

CI: add `CHANGEDETECTION_API_KEY` as a repository secret. The Ansible workflow
forwards it alongside the existing `TELEGRAM_TOKEN` and `TELEGRAM_TO` secrets.
For local runs, export these variables in the controller environment.

Ansible adds `tgram://<bot-token>/<chat-id>` to global notification destinations
without deleting existing ones. Rotating a bot token adds a new destination;
remove the old destination in the UI. Start the bot chat first. Use the UI's
**Send test notification** yourself to verify delivery; deployment sends no test
message. Global destinations can be overridden by watch/tag settings.

Start with 3–5 concrete shop pages, filter to price and availability, then inspect
the snapshots. Default notifications report every change in that filtered block,
including price increases. Configure per-watch conditions for narrower alerts.
See [API documentation](https://changedetection.io/docs/api_v1/) and
[Apprise Telegram](https://github.com/caronc/apprise/wiki/Notify_telegram).

## Publish prices to OneMoreThing

The exporter lives in `dlevchuk/OneMoreThing`: `scripts/sync-prices.py`.
Its README describes automatic reconciliation from the wishlist catalog and
optional shop profiles. Publish those files before enabling synchronization.
Watches are provisioned automatically; explicit UUID mappings are only needed
for exceptions. Sources without exact structured prices need extraction profiles. Prices retain the source currency.

1. On Pi, create `/home/pi/.ssh/wishlist_prices` as a dedicated Ed25519 key
   owned by `pi`, mode `0600`. Add only its public key as a **write-enabled
   deploy key** in OneMoreThing → Settings → Deploy keys. Do not reuse the
   infrastructure SSH key. Install a verified GitHub host key in pi's
   `~/.ssh/known_hosts`; strict host key verification remains enabled.
2. Set `enable_wishlist_price_sync: true` in Pi 4 group vars and supply
   `CHANGEDETECTION_API_KEY`. Rerun the Ansible command above.
3. The role creates a dedicated checkout in `/home/pi/wishlist-price-sync/repo`
   and a private environment file. The systemd timer runs every six hours
   with up to ten minutes jitter and catches up after boot. It fetches/rebases
   the configured branch, reconciles watches, exports observations, and commits
   `data/prices.json`, `data/monitoring-status.json` and `data/price-history.json` when changed. It then
   pushes. SSH deploy-key pushes trigger the existing Pages
   workflow. Protected branch rules must permit this key's pushes, or use a
   branch/workflow appropriate to your repository policy.

```bash
sudo systemctl start wishlist-price-sync.service
systemctl list-timers wishlist-price-sync.timer
journalctl -u wishlist-price-sync.service -n 60
```

The runner rejects a dirty checkout, serializes runs with flock, retries a
previously unpushed commit, and stops on merge conflicts for manual resolution.
An API/parse failure retains the last good observation and timestamp, marks it
as needing verification, publishes valid results for other items, and reports
failure in the journal. No exporter error details or shop responses are published.
No Telegram alerts for exporter/systemd failures are configured by this role.
UI observations older than 24 hours require verification. Watch checks and
publication are separate schedules, so updates can lag by one export interval.

The checkout contains executable code from the wishlist repository: restrict
write access to that repository accordingly. The deploy key, environment and
checkout are outside `/home/pi/docker`; provision the key again after rebuilding
a Pi, while changedetection's datastore is restored by the existing Docker backup.

Set `enable_wishlist_price_sync: false` to stop/disable its timer and retain data. `enable_changedetection: false`
removes the container on a full playbook run, retaining its datastore. To switch
off both, set both flags to false and run the full playbook. Completed gifts must have their mapping removed and
watch paused manually; no privileged wishlist database credentials are used.

Validation without changing hosts:

```bash
.venv/bin/ansible-playbook -i ansible/raspberry/hosts ansible/raspberry/site.yml \
  --syntax-check
```

## Automatic card import and watch provisioning

OneMoreThing now includes **Actions → Add wishlist card from URL**. Enter a
public product URL and select a priority. The workflow extracts title, image and
description from JSON-LD/Open Graph, updates the static catalog, and dispatches
the Pages deployment. Shops with anti-bot/JavaScript-only pages can require a
manual card; the importer stops when reliable metadata is absent. New gift IDs
still require applying the generated catalog SQL to the wishlist database using
the existing documented procedure; no privileged database key is provisioned here.

Once `enable_wishlist_price_sync` is enabled, each timer run reconciles watches
from `data/wishes.json`. Only the card’s `originalUrl` (the «Джерело» link) is monitored.
`localUrl` and URL overrides are ignored; cards without `originalUrl` are skipped.
Old integration-owned watches for replaced local sources are paused, and old
observations from those sources are removed instead of relabeled. Deterministic integration-owned titles allow
recovery after interrupted requests without recreating watches on every run.
Removed/disabled/replaced sources are paused, never deleted; manually created
watches remain untouched. Set `monitoring: false` on a gift to opt out.

The exporter reads exact Product/Offer JSON-LD in the source currency from changedetection's last
HTML snapshot without issuing another shop request. Aggregate price ranges,
unknown/mixed currencies, conflicting variants and absent structured data need a source
profile/explicit extraction rule. Profiles live in `config/shop-profiles.json`
in OneMoreThing; IDs and manual watch UUIDs are optional. Profile keys can be
hostnames or named presets selected by `monitoring.profile`. See its README.
Default watches report text changes and track JSON-LD pricing; configure
`includeFilters` for noisy shops. Telegram defaults are inherited from the service.

`watch-state.json` is stored privately next to the exporter environment, outside
the repository. `data/monitoring-status.json` exposes only gift IDs and short
statuses (`ok`, `disabled`, `needs_review`, `watch_sync_failed`,
`duplicate_watches`). It contains no tokens, watch UUIDs or captured shop HTML.
Deploy the updated OneMoreThing code before the new runner, since the runner
stages this status file as well as prices. The existing deploy-key/API bootstrap
is still required once; subsequent card and watch creation is automated.

## Dashboards, cleanup and price history

The monitoring UI and exporter run on Pi 4 at
`http://raspberrypi.tail72e9f.ts.net:5000`. Homepage on Pi 4 shows the local
container card; Glance on Pi 5 keeps a remote link and HTTP monitor via
`changedetection_hub_url`. Both use the stable Tailscale hostname.

Audit watches with OneMoreThing’s `scripts/audit-monitors.py`, then use
`--prune` to delete confirmed failing integration-owned monitors. Back up the
current datastore before deletion. Preserve and commit the generated
`config/monitoring-disabled.json` so reconciliation does not recreate them.
Pending first checks and unrelated manual monitors are never deleted by the
audit tool.

The exporter appends real successful price observations to
`data/price-history.json`; the publisher stages this file and the site renders
its history as an SVG graph. No prices are fabricated for dates before
recording began.
