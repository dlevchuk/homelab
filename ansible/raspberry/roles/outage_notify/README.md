# Моніторинг перезапусків і мережі

`raspberry-outage.service` постійно перевіряє TCP-доступність `1.1.1.1:443`
або `8.8.8.8:443`. Між циклами чекає 10 секунд; перевірки, NTP і надсилання
додають час. Це перевірка зовнішньої мережі, доступність DNS і Telegram
перевіряється фактичним надсиланням повідомлення.

## Повідомлення

- Запуск після штатного завершення: reboot і poweroff не розрізняються.
- Запуск після нештатного завершення: можливе зникнення живлення, reset або зависання.
- Ping-reboot: маркер береться тільки з журналу з тегом `ping-reboot`.
- Kernel panic / lockup: повідомляється зафіксований факт у попередньому журналі,
  який сам по собі не доводить причину завершення. `Oops` не вважається panic.
- Відновлення інтернету без перезапуску: окреме повідомлення з тривалістю.

`Без інтернету (за перевірками)` — проміжок від першої невдалої перевірки
до першої успішної. Якщо монітор запущено вже без мережі, попередня частина
збою невідома і не входить у цей проміжок. Втрата мережі під час вимкненого Pi
не може бути зафіксована самим Pi. Короткі збої між перевірками можуть залишитися
непоміченими.

У межах одного запуску тривалість рахується монотонним годинником навіть без
NTP. Через reboot потрібні надійні календарні мітки початку та відновлення.
Якщо їх немає, тривалість невідома. Після виявлення мережі на NTP очікується
до 10 хвилин, але час очікування не додається до тривалості збою.

Без спостереження початку мережевого збою повідомлення після boot може показати
`Від останньої активності до виявлення інтернету`. Це оцінка проміжку доступності
Pi, а не виміряний час без інтернету або живлення. При перерваних коротких
запусках цей проміжок включає і час їхньої роботи. Пошук обмежений 10 попередніми
запусками; короткий нештатний запуск — менше 10 хвилин за журналом.
Відсутність або обрізання журналу обмежує визначення причини.

## Збереження та доставка

`/var/lib/raspberry-outage/monitor.json` містить boot ID, поточний мережевий збій
і чергу повідомлень. Зміни атомарно записуються на диск до надсилання.
Подія видаляється тільки після відповіді Telegram з `ok: true`.
Повторні спроби не обмежені шістьма годинами. Затримка доставки після підготовки
повідомлення виводиться окремо, якщо доступний надійний годинник.

Перезапуск сервісу в межах одного boot не створює повторної події запуску.
Кілька boot без мережі залишаються в черзі; для старіших запусків невідомий
час першого виявлення інтернету після саме того запуску не вигадується.
Якщо Telegram прийняв повідомлення, але відповідь загубилась або Pi вимкнувся
до збереження підтвердження, можливий повтор. Черга не має автоматичного
видалення старих подій; тривала недоступність Telegram збільшує її розмір.

Пошкоджений JSON не перезаписується: сервіс завершується з помилкою, яку видно
через `journalctl -u raspberry-outage.service`. Перед ручним відновленням стану
зупиніть сервіс і збережіть копію файла. systemd перезапускає процес після збоїв.

Роль Ansible запускає монітор за наявності Telegram credentials і перезапускає
його після змін. Перший деплой нової версії створить подію поточного запуску.
Heartbeat продовжує працювати окремим таймером.

Перевірки без доступу до Pi або Telegram:

```sh
python3 -m unittest discover -s tests -v
```
